### Cultural reference checks

The [Incredible India festival index](https://www.incredibleindia.gov.in/en/festivals-and-events) is a starting point for region-specific context, not a substitute for consultation with people from the relevant communities. Its current descriptions are useful reminders that:

- [Navratri](https://www.incredibleindia.gov.in/en/festivals-and-events/navratri) has distinct regional observances including Garba, Durga Puja, Ramlila and Kolu. Avoid collapsing these into one pan-Indian visual shorthand.
- [Durga Puja](https://www.incredibleindia.gov.in/en/festivals-and-events/durga-puja) describes a Bengal-centered practice with pandals, artistry, rituals and community life. Any visual treatment should be reviewed with Bengali participants and should not use sacred figures as decorative game tokens.
- [Ganesh Chaturthi](https://www.incredibleindia.gov.in/en/festivals-and-events/maharashtra/ganesh-chaturthi) includes installation, worship and immersion traditions; sacred imagery should not become a numbered ball, mascot, prize marker or generic ornamental border.
- [Eid ul-Fitr](https://www.incredibleindia.gov.in/en/festivals-and-events/eid-ul-fitr) is described as following the new-moon signal after Ramadan, with religious, charitable and community dimensions. Avoid treating a fixed moon icon, one national costume, or a single decorative pattern as representative of every Muslim community.
- [Christmas in India](https://www.incredibleindia.gov.in/en/festivals-and-events/christmas) varies by region and community, and joins worship with local food and celebration. A theme should avoid implying that every Indian Christmas looks the same.
- [Holi](https://www.incredibleindia.gov.in/en/festivals-and-events/holi) has regional forms; the official [Braj Holi](https://www.incredibleindia.gov.in/en/festivals-and-events/rajasthan/braj-holi-festival) description includes distinct traditions tied to place and devotion. Do not reduce the theme to a full-screen powder burst or assume the same motifs everywhere.
- [Onam](https://www.incredibleindia.gov.in/en/kerala) is a Kerala harvest-season celebration with a multi-day rhythm and varied cultural events. Treat it as a Kerala-specific visual package and review details locally rather than using generic “Indian” decoration.
- A previously published [Incredible India Pongal overview](https://www.prod.incredibleindia.gov.in/content/incredible-india-v2/en/destinations/coimbatore/pongal-festival.html) describes a multi-day Tamil Nadu harvest festival with distinct days and practices. Treat that page as a starting point only; verify current details and review Tamil naming, language and imagery with Tamil speakers before design. Do not borrow sacred or agricultural imagery as casual game tokens.

These are guardrails for research and review, not final art direction. The cultural reviewer and exact localized copy/artwork should be named in the Phase A sign-off before those themes are implemented.

## Typography direction

- Keep numbers and ticket cell glyphs highly legible at 360 px mobile width and at projection distance. Use tabular numerals for boards, call history and statistics.
- Prototype a bundled Noto Sans family for interface and ticket data, plus a restrained Noto Serif family for selected English/Hindi display headings. Select exact styles only after side-by-side Hindi shaping, matra spacing, Latin/Devanagari numeral and size testing.
- Never use a decorative display face for the number grid, status, claim controls or small labels. Test line wrapping, fallback and font loading offline; font failure must not shift ticket cells or change their meaning.
- Bundle locally after reviewing the exact upstream OFL files. Do not make runtime rendering depend on Google Fonts CDN availability.

## Calling, motion, accessibility and rendering

- [React Three Fiber performance guidance](https://r3f.docs.pmnd.rs/advanced/scaling-performance) describes render-on-demand for scenes that do not need continuous frames. This fits a short number reveal, while the live board itself should remain ordinary DOM and update from the authoritative socket event.
- [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) calls out conservative VRAM use, context-loss handling, optional extensions and user-selectable quality. A 3D ball must degrade to CSS/SVG/canvas and static current-number presentation if WebGL fails or is disabled.
- [MDN WebGL context loss](https://developer.mozilla.org/en-US/docs/Web/API/WebGLRenderingContext/isContextLost) documents that contexts can be lost due to GPU pressure or device switching. Detect/handle loss, clean up resources and make fallback immediate; do not leave a blank caller panel.
- [W3C reduced-motion technique C39](https://www.w3.org/WAI/WCAG22/Techniques/css/C39) and [WCAG animation-from-interactions guidance](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions) support respecting the platform's reduced-motion preference and providing a way to suppress non-essential movement. The call must appear immediately in text/DOM and remain synchronized even if its animation is skipped.
- [React Three Fiber performance pitfalls](https://r3f.docs.pmnd.rs/next/advanced/pitfalls) recommends reusing geometry/materials, avoiding React state updates in frame loops, and using frame-delta-based motion. If we adopt R3F, keep the animated call ball isolated and avoid per-frame React renders.
- The [Three.js disposal guide](https://threejs.org/manual/pages/how-to-dispose-of-objects.html) explains that geometries, materials and textures need explicit lifecycle cleanup; use its renderer information for leak/perf diagnostics. This strengthens the case for one small, lazy-loaded scene instead of a 3D layer across all routes.
- Preserve visible focus, keyboard operation, screen-reader labels, contrast, touch target size and no-overflow behavior throughout. WCAG 2.2 SC 2.5.8 defines a 24-by-24 CSS-pixel minimum pointer target subject to listed exceptions; apply that as a design check for compact controls. Test game state with animation on/off and WebGL on/off to prove identical numbers, ticket marks, claims and sequence.

Recommendation to test after the gate: provider interface plus three adapters (browser device voice, static/pre-rendered clip, optional cloud synthesis). Audio must be opt-in, default to muted where autoplay is blocked, and never carry the only announcement of a call or win.

## Design decisions to validate during implementation

1. The full 1–90 board, current call, player ticket, active patterns and claim result retain fixed high-priority hierarchy in every theme. Ornament lives around rather than over these elements.
2. A number event updates DOM text/board/tickets immediately from the server event. Optional sound and an approximately brief ball reveal run afterward and never hold, reorder, repeat or synthesize game state.
3. Keep the persistent lobby/caller data in DOM; use a bounded, lazy-loaded renderer only for the hero ball. Consider render-on-demand and dispose GPU assets when leaving live play. Measure initial bundle, total transfer, peak memory and mobile frame behavior before selecting 3D.
4. Theme package validation includes semantic tokens, tickets, call balls, pattern diagrams, dialogs, chat, loading/empty state, contrast and reduced-motion variants; selection cannot touch game or reservation state.
5. Develop Diwali/Holi as initial reference prototypes, then represent cultural differences carefully for all requested Indian, international/seasonal and everyday themes. Require Hindi and English review before release; avoid treating sacred symbols as interchangeable decoration.
6. Keep the host console operationally clear for a projected/large screen while remaining usable on mobile. Host-only actions stay grouped and status labels never rely on color alone.
