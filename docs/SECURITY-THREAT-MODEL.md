# Multi-tenant security review (manual)

Date: 2026-11-01. This is a source-led manual review performed by the implementation agent; it is **not** an independent penetration test or L3 review. No separate security-review tool was available in this environment. A qualified external reviewer should examine the production deployment, database roles, proxy/cookie setup, and the complete authorization diff before launch.

## Trust boundaries and invariants

- Super Admin is the only global application principal. Owner routes are intentionally platform-wide and use the existing owner session, MFA, CSRF, and audit controls.
- Moderator is a distinct principal. Every protected request checks a live session, active status and enrolled MFA. Every data operation resolves the requested instance grant and current permission from PostgreSQL; client-supplied roles and instance ownership are not trusted. Room operations then resolve the room's `game_instance_id` and compare it to the authorized instance. Foreign room identifiers are non-enumerating 404s.
- Player and host authority comes from a server-validated session tied to one room and seat. Session verification checks the room code; host-only commands check the live host socket. A socket already attached to one room cannot join/create/resume into another room. Same-room join remains idempotent for legacy client compatibility.
- Durable game entities are keyed by authoritative room/game relationships. `room_members`, sessions, tickets, games, calls, claims, awards, and schedules are read/written by room code (and game number/player id under that room); FK and uniqueness constraints retain those relationships. They do not independently select a tenant from a client-supplied player/ticket/game id.
- Background recovery operates on one room bundle at a time, validates its stored game history and tickets, and freezes inconsistent rooms. Scheduler actions use room id and durable schedule rows. Backup/restore is a platform-owner operational boundary, not an end-user API.

### Socket event inventory

The server event registration in `server/net/socket.js` covers room creation/join/reconnect and session rotation; room state/leave; host game controls and pattern configuration; player claims and ticket selection; chat send/history; and separate moderator room controls. The legacy client event deny-list remains covered by the security probe. Event payload validation runs before the attached-socket room-switch guard, preserving stable `BAD_PAYLOAD` responses. Moderator socket commands reauthorize on each action.

### Deliberate permissions with no supported operation

Ticket mutation is unsupported and therefore has no `tickets.manage` mutation endpoint. Tickets are generated and assigned server-side for each game; adding a mutable inventory would create new semantics and history risks. Moderator room detail can reveal ticket details only when its read permission allows it. There is no moderator ticket CRUD, sales, or shared pool. No additional destructive player action is provided beyond removal from an eligible non-completed/non-closed room; room membership history is retained.

## Attack coverage and remaining scope

Automated integration coverage uses live PostgreSQL fixtures for Regular and Bumper, with valid foreign room/player IDs. `tests/moderator.test.js` checks protected anonymous access, CSRF/MFA, assigned/read-only/unassigned/suspended/revoked behavior, foreign room and player IDs, instance history/report boundaries, settings allowlist, player-removal scope, room-switch socket rejection, room-bound reconnect rejection, MFA IP binding, recovery single-use, and active HTTP/socket grant revocation. `tests/instances.test.js` recovers Regular, Bumper, and Legacy rooms in a new registry and verifies durable ownership remains unchanged. Existing realtime and security-probe suites cover player/host session, event authorization, ticket privacy/claim validation, and room broadcast separation.

The focused `tests/moderator-instance-id-isolation.test.js` adds an authenticated Regular-only HTTP matrix against foreign Bumper, archived Legacy, and nonexistent instance IDs. Five list/read routes plus player detail, booking detail/cancel, settings update, and room creation return non-disclosing 404s for all three targets (30 denied requests). Unknown-room detail, start, and player-removal requests also fail closed. The test exercises audit writes for nonexistent IDs and asserts that these attempts retain bounded IDs in metadata without placing invalid foreign keys in `platform_audit`. Booking list filters verify the granted session returns its reservation while a Bumper session or unknown session returns none. Malformed session/status filters and repeated `sessionId`, `status`, or `search` query parameters return 400 rather than silently widening the query. Its disposable schema is dropped after the run.

This is not a full role-by-role Cartesian fuzz campaign across every endpoint and every identifier. In particular, dedicated valid-foreign-ticket, game, claim, award, player-session and host-session HTTP endpoint attacks are inapplicable where no such moderator/API lookup exists; the player/host engine tests cover same-seat ticket/claim behavior. No moderator ticket mutation path exists. Super Admin's cross-instance access is intentionally global. This coverage is evidence for current code paths, not a proof against future route/query additions.

## Recovery and backup limits

Moderator recovery is owner-initiated: the Super Admin suspends the account and issues a random single-use token with a 30-minute expiry. Only the token hash is stored. Completion changes the password, clears old MFA enrollment, reactivates the account, revokes sessions and socket tickets, consumes the token, and audits the action. The moderator must re-enroll MFA before privileged access. There is no self-service email recovery because no verified recovery channel exists. If the owner account itself is unavailable, recover it through the documented offline owner-account/database procedure; moderator recovery must not be used to bypass owner MFA. Recovery token delivery is intentionally an out-of-band operational responsibility.

The standard backup and restore check ran against the local public schema: 28 tables, 12,964 rows, 10 migration-ledger entries restored in a throwaway database. The source had no populated moderator fixtures, so a separate controlled drill used `scripts/moderator-backup-drill.mjs` to create synthetic accounts, grants, sessions, socket tickets, recovery tokens, and platform audit rows in an isolated schema, dump it, restore into a throwaway database, verify active and revoked/consumed states, then remove both scratch objects. Result: **PASS** (2 accounts, 3 grants, 2 sessions, 2 recovery tokens, 1 consumed socket ticket, 3 audit rows). This proves the local PostgreSQL archive/restore path for the current moderator records; it does not prove production backup storage, retention or key escrow. Separately verify the MFA encryption key escrow before launch.

## Findings

1. **Fixed:** a player/host socket could join a second Socket.IO room after attaching to a first room, leaving a broadcast membership behind. The socket now rejects cross-room create/join/resume; same-room `room:join` remains idempotent.
2. **Fixed:** MFA challenge IP mismatch did not spend the challenge attempt budget. Mismatches now increment and consume after the configured limit.
3. **Fixed:** a global migration advisory lock caused unrelated test schemas to queue and time out under parallel test execution. The lock is now keyed by schema, retaining same-schema serialization.
4. **Fixed:** denied moderator requests for unknown instance/room path IDs could fail while writing `platform_audit` because the attempted IDs violate audit foreign keys. Audit foreign-key values now resolve only existing rows; bounded attempted IDs remain in metadata. The focused 30-request regression matrix passes against PostgreSQL.
5. **Residual deployment review:** database role privileges, network exposure, secret rotation/escrow, and actual production proxy/cookie settings need review in the target environment. This local source review cannot attest to those controls.


## Expanded moderator identifier matrix (2 November 2026)

The durable route regression now tests valid Bumper and archived Legacy room/player IDs through a Regular grant, Regular room IDs through foreign instance paths, all five room actions, player removal, booking read/cancel and session assignment, plus unknown room/player/reservation/session IDs. Denials leave room status, memberships, reservation status and reservation audit unchanged; the test also confirms the moderator instance directory returns only its explicit grant. The four moderator-focused suites passed **5/5** against disposable PostgreSQL 17.11. This is expanded route coverage, not exhaustive Cartesian fuzzing or an independent L3 review.

## Owner-only runtime health projection (2 November 2026)

Operational counters shown in the Super Admin overview and `/api/admin/health` are served behind the owner-session gate and `Cache-Control: no-store`. The response includes only readiness facts and bounded counts for migrations, lease state, rooms, scheduler and pool; it does not serialize connection strings, lease tokens, passwords, or raw database errors. HTTP tests verify unauthenticated denial and secret omission. The public `/healthz` remains a separate probe endpoint and returns only the documented readiness report; external monitoring and alert delivery still require target-host configuration.
